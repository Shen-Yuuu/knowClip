# 原型 A/B 真机报错排查记录

## 背景

2026-08-29 00:11 真机运行原型 A、B 时采集到 hilog 报错。本文记录排查结论、证据链与复测步骤。

## 报错现象

原型 B（选图后开始识别）出现以下错误链：

```text
C03D00/utils_base      path (media/Photo/26860/IMG_.../screenshot_xxx.jpg) to realpath error: No such file or directory
C02B61/ImageSourceStream  [FileSourceStream]input the file path exception, errno:2.
C02B61/ImageSourceNapi    CreateImageSourceExec error
A00001/OCRService         OCR failed with code -1 after 1ms
```

原型 A（图库单图分享到知微）表现为分享确认页显示“未解析到可保存的分享内容”，无法保存。

日志中其余错误（CODE_SIGN XpmIoctl、calculateResourceType deviceType is empty、WMS root is null、SetWindowType permission denied、WMSCompat、RegisterClientDeathObserver、AceTransform 缺 so、PARAM_WATCHER、DMS GetScreenSession、AppKit null assertThread 等）均为系统框架噪音，真机常见，与本项目代码无关，不需要处理。

## 根因

图库与 Photo Picker 提供的是受系统授权的**媒体 URI**（`file://media/Photo/<id>/<name>`），不是应用可直接按路径读取的文件路径：

1. **原型 B（旧代码）**：`image.createImageSource(uriString)` 把媒体 URI 当普通路径。图像框架剥掉 `file://` 前缀后对 `media/Photo/...` 做 realpath 解析失败（ENOENT），无法创建 ImageSource，OCR 以 code -1 结束。
2. **原型 A（旧代码）**：解析器只读取 `record.uri`，并把所有 `record.content` 当文本；图库分享场景中 URI 位于 `record.content` 或 `want.uri`，导致图片记录被丢弃。
3. **为何修复后真机仍报旧错误**：媒体 URI 兼容修复（见 `docs/plans/2026-08-28-prototype-media-uri-compatibility-design.md`）已于 08-28 写入工作区并编入 14:47 构建的 HAP，但该 HAP 未签名，设备上安装的仍是修复前的旧包。

## 证据链

1. 错误签名唯一匹配“路径字符串进入 createImageSource”。修复后的 `OCRService` 只向 `image.createImageSource(sourceFile.fd)` 传文件描述符（数字），不可能产生 `FileSourceStream` 的路径异常。
2. `OCR failed with code -1` 中 -1 来自 `Number(error.code)` 为 NaN，即无 code 的普通 JS Error——与 ImageSourceNapi 抛错行为一致；若是修复后 `fileIo.open` 失败，会记录真实错误码（如 13900002）。
3. 对 08-28 14:47 构建的 `entry-default-unsigned.hap` 解包校验：`ets/modules.abc` 中包含三处修复的标志字符串（`Failed to close OCR source image`、`using Want URI fallback`、`Copying shared image to`、`Parsed share data: records=`），证明源码修复已编译进产物。
4. `build-profile.json5` 的 `signingConfigs` 为空，hvigor 明确警告跳过签名；`hdc list targets` 当前无设备连接。因此设备从未安装过包含修复的构建。

## 已落实的修复（工作区未提交改动）

- `services/ShareDataParser.ets`（新增）：把 Share Kit 记录归一为 ShareData——`record.uri` 优先；图片类 UTD 的 `record.content` 视为图片 URI；文本与链接仍按文本处理并提取首个 HTTP(S) URL；全空时回退 `want.uri`。
- `shareextensionability/ShareExtAbility.ets`：`onSessionCreate` 改用解析器，`getSharedData` 抛错或内容全空时回退 `want.uri`，日志只记录记录数、UTD 与字段存在性，不记录完整私人 URI。
- `services/FileService.ets`：`fileIo.open(uri, READ_ONLY)` 打开源媒体 URI，`copyFile(fd, fd)` 复制到沙箱，`finally` 中关闭两个描述符。
- `services/OCRService.ets`：`fileIo.open` 打开 Picker URI 后以 `image.createImageSource(fd)` 解码，`finally` 依次释放 PixelMap、ImageSource 并关闭源描述符。
- `entry/src/test/LocalUnit.test.ets`：新增 4 个解析器单测（记录 URI、content 图片、文本+URL、want.uri 回退）。

## 部署与复测步骤

1. 连接真机后，在 DevEco Studio 中 **Run 'entry'**（自动签名并安装新包）。命令行构建因未配置签名会跳过 SignHap，无法直接安装。
2. **原型 B**：选图 → 开始识别。预期：
   - hilog 中不再出现 `path (...) to realpath error` 与 `CreateImageSourceExec error`；
   - 返回识别文本或真实 OCR 引擎错误码；若 `fileIo.open` 失败将显示真实错误码（如 13900002 为 ENOENT），据此继续排查。
3. **原型 A**：系统相册单图分享 → 知微。预期：确认页显示图片、“保存”可用，保存后显示 `✅ 已保存到本地收件箱`。
4. **回归**：分享一段含 HTTP(S) 链接的纯文本，确认文本与链接均被解析并可保存。

## 后续候选排查方向（若复测仍失败）

- `fs.open` 打开 `file://media` URI 需要系统授予的临时读权限；确认输入必须来自 Picker/分享授权路径，而不是自行拼接。
- 关注新的真实错误码：13900002（文件不存在/权限）、13900042（未知错误）、7400201（图像源创建失败）等，按码定位。
